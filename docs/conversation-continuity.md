# 대화 연속성 구조 — 2026-10-19

## 생성 경로

`generatedTurn` → 원문/기억/상태 조회 → `conversationContext.prepare` → `llmService`의 실제 API 호출 1회 → 응답·기억 검증 → SQLite 원자적 저장.

같은 호출에서 모델은 다음 대화 상태와 새 기억 항목, 실제 답장을 JSON으로 생성한다. 사용자에게는 `reply`만 전달한다. 내부 상태는 추론 과정이 아니라 현재 주제, 캐릭터 감정, 사용자가 표현한 감정(불확실하면 추정), 관계의 거리, 직전 상호작용을 담은 짧은 기록이다. 모델은 계속 `gemini-3.1-flash-lite`, 출력 상한 16,384, LOW thinking을 사용한다. 모델을 바꿔도 같은 기억 계층을 사용할 수 있다.

## 세 가지 기억 계층

1. **최근 원문**: 이전 12개 제한을 없애고, 새 입력을 포함해 최대 60개 메시지·24,000자 범위로 원문 전체를 선택한다. 예산 때문에 문장 일부를 잘라 넣지 않는다.
2. **누적 항목**: 사용자 사실/취향, 캐릭터 자신의 취향, 함께 나눈 사건·장난·약속, 중요한 미해결 주제, 명시적인 대화 합의를 별도로 저장한다. 각 항목에는 원문 ID, 고유 기억 ID, 가능한 경우 원문 시각이 있다.
3. **상태와 이력**: 요약과 현재 감정·관계 상태를 저장하고, 성공한 각 답변의 상태 변화를 별도 이력으로 보존한다. 주제가 달라졌다고 감정의 원인이나 화해 과정을 삭제하지 않는다.

오래된 원문은 한국어 글자 조합과 단어 중복에 기반한 가중 검색으로 관련 앞뒤 메시지를 최대 12,000자까지 추가한다. 오래된 활성 기억 항목과 과거 상태도 관련성을 기준으로 다시 찾는다. 새 구조가 없던 기존 방은 첫 대화 일부와 오래된 구간을 순차 검토하여 점진적으로 보충한다. 이전 브라우저의 `memorySummary`나 키워드로 만든 `userFacts`를 신뢰 가능한 서버 기억으로 승격하지 않는다.

## 덮어쓰기 방지

실제 30턴 평가에서 '전체 기억을 모델이 다시 쓰는 방식'은 초기 사건이 최근 요약으로 밀려나는 문제가 확인됐다. 따라서 모델 출력의 항목 배열은 **새로운 추가분**이다. 빈 배열은 기존 항목을 삭제하지 않는다.

- 기존 항목은 서버가 유지한다. 정정/철회는 고유 기억 ID와 이번 사용자 원문을 근거로 명시한다. 해결된 미해결 주제만 이번 AI 답변으로 닫을 수 있다.
- 이름과 차 취향을 같은 메시지에서 들었어도 각각 다른 기억 ID를 갖는다. 취향을 정정한다고 이름까지 지워지지 않는다.
- 정정된 과거 항목은 비활성 상태로 남아 이력을 보존하며 현재 사실 검색에서 제외한다.
- 현재 프롬프트에 넣는 목록에는 범위가 있다(사용자 사실 32, 캐릭터 사실 24, 사건 32, 미해결 주제 12, 합의 24). 목록 밖으로 밀린 항목도 DB에서 지우지 않는다. 검색은 최근 활성 항목 1,000개와 상태 이력 200개 내에서 수행한다.

`conversation_state`는 현재 요약/상태와 revision, `conversation_memory_items`는 항목과 정정 이력, `conversation_state_events`는 답변별 상태 변화를 보관한다. 사용자·캐릭터 ID를 함께 키로 사용한다.

## 근거·저장·과금

- 사용자 사실과 합의는 사용자 발화만, 캐릭터 사실은 AI 발화만 근거로 받는다. 존재하지 않는 근거 ID나 잘못된 역할의 인용은 실패로 처리한다. 새 인사 생성 지시는 사용자 신상 근거가 아니다.
- Gemini JSON schema는 가능한 원문 ID를 제한한다. 기억 항목 ID의 유효성은 서버에서 검증한다. 큰 기억-ID enum은 Gemini schema 복잡도 제한에 걸려 사용하지 않는다.
- 성공한 답변, 하트 차감, 추가 기억, 정정, 상태 이력, 재시도 결과를 같은 SQLite 트랜잭션에 기록한다. 검증·API·저장 실패 시 기억과 하트를 변경하지 않으며 고정 대사로 대체하지 않는다.
- 같은 요청 ID를 다시 보내면 저장된 답변을 재사용하며 기억도 중복 갱신하지 않는다. 방 삭제 중 생성이 끝나도 revision 검사로 저장/과금이 취소되어 방이 다시 살아나지 않는다.
- 번호 연결 시 기억도 계정으로 이동한다. 방 삭제 시 해당 방의 현재 기억·항목·상태 이력을 지운다. 기존 운영자용 메시지 보관은 기존 정책대로 별개다. 계정 전체 파기 작업 시 세 신규 테이블도 사용자 ID 기준으로 함께 처리해야 한다.

## 대화 지침의 변경

감정과 맥락 → 성격 → 타이핑 순으로 우선순위를 정리했다. 관계는 매번 자동으로 가까워지지 않고, 사용자의 평가를 과거 사실로 무조건 인정하지 않는다. 사용자가 다른 주제로 넘어간 뒤 사소한 질문을 재촉하지 않는다. AI·캐릭터 설정 질문에는 공개 프로필을 편하게 설명하고, AI임을 부정하거나 질문을 무례함으로 취급하지 않는다. 날짜는 발화 시각과 서버 시각을 함께 보고 해석한다.

말높임은 사용자의 명시적인 반말/존댓말 요청을 별도 메타데이터로 보존한다. 기억의 합의 항목이 참조하는 원래 사용자 발화도 필요할 때 다시 확인한다. 선물 카드의 정중한 표현이나 이전 AI의 말투 실수를 새로운 변경 합의로 취급하지 않는다.

## 검증

- 자동 검사: 원문 예산/무절단, 과거 원문 검색, 사용자/캐릭터 근거 구분, 인사 제외, 빈 추가분의 과거 기억 유지, 정정 시 무관한 항목 보존, 계정/방 분리, 재시작, 번호 연결, 방 삭제 중 생성 취소, 원자적 과금/기억 저장, 동일 요청 재전송, 불완전 JSON/부정확한 근거/통신 실패의 미차감.
- 실제 API 평가: `node server/scripts/evaluate-continuity.cjs --live`. 별도 임시 SQLite에서 합성 계정으로 30턴을 실행한다. 원문 앞부분을 의도적으로 줄이고 새 프로세스로 재개하여 과거 기억을 사용하도록 한다. 실제 고객 계정이나 운영 DB를 사용하지 않는다. 모델 비교 시 동일 스크립트에 `GEMINI_MODEL`을 달리 지정할 수 있다.
- 확인한 사례: 팀장이 주말에 준비한 자료의 성과를 가로챈 원인과 서운함/화해 과정, 보리차에서 옥수수차로 바뀐 취향, 이름, 비 오는 토요일의 미술 전시 계획, 반말·호칭·이모지 합의 회수.

구조가 감정 판단의 완벽함을 보장하지는 않는다. 근거 역할 검증은 해당 메시지가 실제로 존재하는지를 확인하는 장치이며, 모델의 모든 의미 해석이 옳음을 증명하지는 않는다. 검색은 임베딩 기반 의미 검색이 아닌 가벼운 어휘 검색이고, 기억에는 크기 제한이 있다. 품질 판단은 단일 답변 성공 여부와 구분하여 여러 턴에서 계속 평가한다. 기억 출력과 긴 입력이 추가되므로 API 입력/출력 비용과 응답 시간은 이전보다 늘 수 있으나, 사용자 하트 단가는 변경하지 않았다.

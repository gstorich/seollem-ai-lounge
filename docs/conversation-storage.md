# 대화 저장과 복구

2026-10-22 도입. R2는 `azitchat-private/v1` 전용 접두사를 사용한다. 헤이즈 객체는 변경하지 않는다.

- 대화는 SQLite에 우선 원자적으로 기록한다. 5분마다 미보관 메시지를 방·사용자 구분 없이 새 메시지를 최대 500개씩 하나의 파일로 묶어 R2에 압축·AES-256-GCM 암호화하여 저장한다. 업로드 뒤 다운로드·복호화·SHA-256 검증에 성공해야 보관 참조를 확정한다. 실패하면 다음 실행에서 재시도한다.
- 통합 파일은 서버 전용 비공개 암호화 객체이며 클라이언트에 직접 전달하지 않는다. 메시지별 사용자·방·객체 내 위치 참조로 해당 방의 기록만 반환한다. 기존 방별 파일과 신규 통합 파일을 모두 조회할 수 있다. 방 100개에서 각 1개씩 쌓여도 배치 1개면 PUT 1회 + 검증 GET 1회다. 500개 초과 시 여러 배치로 나눈다.
- 운영 계정 JSON은 방당 최근 120개, 계정 조회 응답은 최근 40개만 포함한다. 과거 대화는 인증된 `/api/account/rooms/:id/messages?before=...`에서 40개씩 조회한다. 최근 기록은 운영 DB, 정리된 과거 원문은 R2에서 읽는다. R2에만 남은 기록 조회 실패 시 503을 반환하며 빈 메시지로 대체하지 않는다. 로컬 원문이 남은 기록은 R2 장애 중에도 조회 가능하다.
- 로컬 원문은 최소 7일간, 방별 최근 120개는 기간과 관계없이 유지한다. 두 보호 범위를 모두 벗어난 메시지는 R2 재다운로드·체크섬·소유자·방·ID·시각·원문 일치 검증 후 SQLite 원문을 sender/topic 분류만 남긴 색인으로 치환한다. R2 장애·불일치 시 해당 객체의 원문은 정리하지 않으며 작업 실패를 기록한다. 정리된 답변의 중복 요청 캐시도 본문 대신 원문 참조를 남겨 재차 차감 없이 복원한다.
- 색인·계정·하트·현재 기억과 기억 변경 이력 등 운영 데이터는 OCI에 남는다. R2는 과거 원문 보관소이며 OCI 디스크 사용량이 0이 되는 구조는 아니다. 오래된 원문이 포함된 기존 로컬 백업은 3일 보존 정책에 따라 순차 삭제된다.
- 어드민 과거 대화는 100개 단위로 원문을 읽는다. 주제/흐름 통계는 정리 전에 계산한 태그를 사용한다. 과거 원문 검색은 요청 시 R2를 500개 색인 단위로 조회하므로 대량 기록의 전체 검색은 느릴 수 있다. 별도 검색 엔진·원문 검색 인덱스는 아직 없다. 이전 약속의 근거와 알림 받은 메시지도 동일한 인증된 서버 원문 조회를 사용한다.
- 휴대폰 연동 시 보관 참조를 함께 이전하고, R2 객체의 이전 소유자는 서버 alias로 검증한다. 서로 다른 사용자의 메시지가 묶인 객체는 클라이언트에 전달하지 않는다.
- 초기 디스크 공간 회수는 검증된 백업 이후 `node server/scripts/reclaim-database.cjs <sqlite-file>`로 수행한다. 기존 디스크 여유가 DB 크기의 3배+64MiB 미만이면 실행하지 않는다. 무결성 검사와 VACUUM 후 incremental auto-vacuum을 사용하며 이후 정리 작업은 최대 256페이지씩 회수한다. 신규 OCI 볼륨·서버를 만들지 않는다. 디스크 사용량과 OCI 무료 자원 할당량은 별도로 확인해야 한다.
- `seollem-archive.timer`: 5분마다. `seollem-backup.timer`: KST 03/09/15/21:30 이후 5분 내.
- DB는 SQLite backup API로 일관된 사본을 만들고 integrity_check를 확인한다. 8MiB 단위로 암호화하여 R2에 업로드하고 각 부분을 다시 읽어 확인한다. 마지막에 검증 manifest를 기록한다.
- 로컬 3일, R2 6시간 간격본 7일, KST 03시 생성 일일본 30일. 원문 보관과 백업 보존 기간은 다르다. 삭제 요청은 R2 원문과 복원 후 재삭제에도 적용해야 한다.
- 비밀 설정 `/etc/seollem-ai-lounge/storage.env`는 저장소에 커밋하지 않는다. R2 객체만으로 복호화할 수 없다. 복구 키는 별도로 관리한다.

복구는 운영 DB에 덮어쓰지 말고 새 경로로 내려받은 후 점검한다:

```
node server/scripts/backup-store.cjs restore <manifest-object-key> /secure/path/restore.sqlite
python3 -c "import sqlite3; c=sqlite3.connect('/secure/path/restore.sqlite'); print(c.execute('pragma integrity_check').fetchone())"
```

복구 검증 후 점검 시간에 앱을 중지하고 DB/WAL 처리·권한·삭제 요청 재적용을 확인한 후 교체한다. 실행 실패는 systemd 실패 상태 및 journal에 기록된다. 상태: `systemctl status seollem-archive.service seollem-backup.service`.

## 시스템 안내와 대화 종료 (2026-10-22)

- `sender=system`은 캐릭터 발화가 아닌 중앙 안내다. 생성 오류·콘텐츠 접근 안내·상대 퇴장도 대화 기록에 포함해 재입장, 새로고침, R2 과거 조회, 어드민에서 복원한다. LLM 문맥과 사용자 대화 횟수에는 포함하지 않는다.
- 실제 API 응답이 `roomLeft=true`이면 최종 답변·하트 차감·퇴장 시스템 메시지·서버의 방 종료 상태를 한 트랜잭션으로 저장한다. 클라이언트 타이핑이나 현재 화면과 무관하다. 상대 퇴장은 방을 목록에서 삭제하지 않는다.
- 재입장 시 종료 안내와 입력/선물 차단을 복원한다. 늦은 스냅샷으로 종료 상태를 해제할 수 없다. 명시적으로 사용자가 방을 삭제하면 서버 상태와 예정 작업을 정리한다. 이미 종료된 요청 재생은 재차 과금하지 않으며 새로운 전송/선물/인사는 모델 호출 전에 거절한다.
- 기존 퇴장 응답 기록이 남고 아직 저장된 방은 서버 시작 시 안내를 보완한다. 사용자가 삭제한 방이나 그 뒤 새 대화가 시작된 방은 복구하지 않는다. 과거에 화면에만 표시되고 어떤 기록에도 남지 않은 오류 안내는 소급 복원할 수 없다.

## 선물 답장 (2026-10-22)

- 선물도 실제 대화와 동일한 API·최근 원문·관계·기억을 사용한다. 생성 스키마에서 3~4개 문자열 배열을 요청하며, 고정 선물 문구 목록을 호출하지 않는다. 사용자의 명시적 말높임 요청이 최우선이고, 그 외에는 사용자가 쓴 존댓말·선물 발송 문구·과거 선물 반응이 아닌 캐릭터의 최근 일반 발화를 기준으로 말높임을 유지한다.
- 서버 카탈로그의 선물만 보내고 사용자 메시지가 없으면 고정 발송 문구의 입력 분류 호출을 생략한다. 사용자 메시지는 입력 확인을 거친다. 생성 후 출력 확인과 AI 기억 기록을 병렬 처리하며, 검증·원문/기억 저장·하트 차감을 모두 확정한 뒤 응답한다. 오류 시 가짜 반응이나 차감은 없다.
- 화면은 즉시 ‘전송 중’ 카드만 보여주며, 확정 전 카드나 비용을 저장하지 않는다. 반응은 생성 후 첫 메시지 즉시, 이후 90~190ms의 입력 간격과 30ms의 호흡으로 전달한다. 일반 대화의 타이핑 시간은 유지한다.
- 정식 저장은 전체 원문과 `bubbles` 배열을 함께 보관한다. 재입장 시 3~4개 말풍선으로 복원하며, 오래된 중복 요청 캐시는 본문·말풍선 배열을 모두 R2 참조로 바꾸고 재요청 때 다시 읽는다.
